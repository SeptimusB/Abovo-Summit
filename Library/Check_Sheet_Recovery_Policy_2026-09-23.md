# Check Sheet, recovery policy and integrity reporting — tests 2.72–2.76

## User-visible policy

- An unresolved, freshly calculated Check Sheet failure sets a red, clickable `(Check sheet)` prefix beside the company heading in group interfaces (including DIT and Analyser) and the File Instance summary. There is no new failure popup. Existing explicit close/save decision dialogs are not removed.
- Clicking the prefix opens the **same model**, Assumptions / Global Assumptions / Check Sheet, using its XML mapping. A workbook without that interface can fall back to its Check Sheet worksheet. No fixed CSID is assumed. Mapped-table worksheet bindings now participate in interface routing.
- By default the failure pauses recovery autosaves immediately at the Check Sheet stage, before the potentially interrupted remainder of the integrity scan. It preserves the last completed recovery. Ordinary Save and Save As remain available and do not certify a repair.
- Recovery backup Options adds **Continue autosave if Check Sheet error?**, off by default. When enabled, the usual unsaved-user-input, idle, timing and transaction gates still apply, but the Check Sheet hold no longer blocks recovery. The warning and remembered failure remain. A later recovery may therefore replace the previous backup with one containing the known errors. Turning the option off reinstates the hold immediately.
- The failure record is stored in local user settings keyed by case-insensitive absolute plan path. It survives closing/reopening in this Windows account, follows Summit Save As, and is consulted for a recovered plan's recorded original path. It is not embedded into the business plan and is not a cross-machine/client-wide lock. Settings errors fail closed where persistence cannot be established and are reported explicitly.
- An input correction, an ordinary save, an old scan, or an uncalculated scan cannot clear the warning. A fresh current Check Sheet pass can. A presentation failure cannot prevent recording the hold.

## Workbook overrides

The workbook keeps E as `Check` even after an override. C contains the unlocked validated Yes/No choice, while D applies the override with `IF(Crow="Yes",0,Brow)`.

Summit accepts an override only when that actual workbook structure is verified: non-zero numeric raw count, unlocked non-formula Yes choice with native Yes/No list validation, zero numeric effective count, and the matching D formula. Accepted overrides are listed separately in the integrity report, not treated as failures. Formula errors, unrelated zeroes and unknown override structures remain findings. There is no blanket suppression based on a nearby Yes or a zero.
