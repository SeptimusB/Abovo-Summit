# Recovery backup trial — Summit 2.66

## User contract

Opt-in `Options → Recovery backup → Enable backup save`, default interval 10 minutes, selectable 1–120. One `<original stem>_recovery.xlsm` is retained in the original plan's folder. Normal Save remains the normal business-plan save. Recovery does not clear unsaved changes, change the working filename, discard Undo or overwrite the original.

Only committed edits are saved. The timer polls every five seconds, waits for 15 seconds without keyboard/mouse-button/wheel activity, and defers for active editors, modal dialogs, saves, progress operations, grouped edits, structural mutation and unhealthy/recovery/read-only models. It skips clean models and already-backed-up revisions. Save As resets its target and interval; closing a model removes its schedule. This is **idle-scheduled**, not background workbook access: native serialization still briefly occupies the UI thread, with progress notification.

Opening the original offers a **newer**, owned recovery copy (Yes/No/Cancel). The original is never automatically replaced. Recovered models recalculate through the existing pending-results gate, are marked unsaved, display a recovery warning and redirect Save to Save As. The dialog suggests the original folder and filename, restricts the result to XLSB and requires overwrite confirmation. Users may choose a different filename. A successful normal Save As removes the recovery guidance and refreshes the FileInstance summary.

The prior session's last 1,000 history rows are embedded in a separate standard custom XML part, with descriptions/old/new values; long fields are capped at 2,048 characters and labelled as truncated. Opening recovery offers the History interface. These entries are **read-only audit history**, not serialised Undo commands. New edits in the current session retain normal Undo/Redo. History is not guaranteed to describe unjournalled direct spreadsheet/structural operations; the workbook itself remains the recovery source.

Recovery identification currently expects its generated sibling path and source marker. Keep that name/location when testing recovery discovery. Ordinary XLSB saves are not treated as recovery copies merely because preserved historical custom properties remain in the package.

## Safety and implementation

- `RecoveryBackupManager`: per-model timer/revision state, persisted per-user options, idle/busy guards and progress/system messages.
- `RecoveryBackupStore`: stream XLSM save to a unique temporary file, flush, metadata/history preparation and owned-destination verification before atomic replacement. A collision with an unrelated file is refused. A failure retains the previous complete recovery.
- `ExcelModel.WriteRecoverySnapshot`: restores native Modified, dirty flag, calculation revision/mode, custom/built-in properties and working paths; does not perform XLSB formula preflight or full calculation.
- `RecoveryHistoryStore`: bounded XML readers, DTD/external entity prohibition, known schema only, no object or executable history deserialisation. Standard custom XML coexistence preserves existing model/SharePoint parts. Signed packages require a separate signing workflow and are not silently patched.
- Full-model open now checks the spreadsheet engine's Boolean LoadDocument result, avoiding a misleading missing-sheet diagnostic when import itself failed.
- No Excel installation or macro execution is required for recovery saving. XLSB Save As still uses existing formula compatibility and save policies. Third-party readers may see pending caches until recalculation; VBA-enabled Excel opening normally follows the model's own rebuild policy.

### Direct conversion issue discovered during validation

DevExpress 25.2.4 exported 64,820 `cm=1` dynamic-array cell metadata references from the frozen AGL XLSB without their `xl/metadata.xml` part. Native reimport failed inside `FormulaDestination.IsDynamicArrayFormula`; the ordinary load path originally disguised that as a missing Global Assumptions sheet. The history custom XML was not the cause.

Both repository masters and the frozen AGL file have the identical 117-byte, single-XLDAPR binary metadata profile. `RecoveryXlsmCompatibility` recognises this **exact** profile at open time. For a private recovery export missing XML metadata, it verifies that all emitted cell metadata references are the supported single record and that no value-metadata references exist; then supplies the equivalent metadata generated by DevExpress's public dynamic-array API. Only the metadata part, content type and relationship are added. Worksheet bytes/formulas are not rewritten. Existing XML metadata is untouched; unknown or contradictory profiles fail safely rather than being guessed. This is deliberately a narrow compatibility bridge, not a general BIFF12 metadata converter.

The Excel-resaved XLSM baselines used in the separate format benchmark already contained XML metadata, so that benchmark did not expose this direct-conversion defect.

Primary references: [DevExpress LoadDocument result and import exceptions](https://docs.devexpress.com/WindowsForms/DevExpress.XtraSpreadsheet.SpreadsheetControl.LoadDocument%28System.String%29), [DevExpress import diagnostics support answer](https://supportcenter.devexpress.com/ticket/details/q576046/spreadsheet-control-and-doc-server-loaddocument-returning-false-with-no-explanation), [Microsoft dynamic-array metadata definition](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/d1ef676d-d970-4ddd-b642-62f5e0c291e0), [XLSB metadata block stores](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xlsb/422e72ca-98c0-47d1-8c5a-6bb4293a1449). Installed licensed vendor source was inspected locally to identify the omission; no vendor source was copied into the repository.

## Recovery notices and shared splash layout

Every scheduled save shows **Saving recovery copy**, the plan filename, and an explanation that the original is unchanged, before serialization starts. A brief **Complete** message follows success; failure displays **Not saved** and points to System Messages. Both start and completion/failure are recorded in System Messages. Completion remains visible for approximately 900 ms.

The scheduler resolves a live visible Summit owner even when `Form.ActiveForm` is absent. If all windows are minimised or no notification can be shown, it defers instead of saving silently; restoring a window makes a due backup eligible again. It does not activate Summit or restore minimised windows programmatically.

The shared `WaitFormA`, also used for file opening and other long operations, now uses DevExpress's native ProgressPanel wrapping/auto-height with bounded content width. It remeasures on message/DPI changes, stays inside the monitor's working area, scrolls exceptionally long messages, and shrinks again for completion. Docking/scrollbar width changes explicitly trigger native height remeasurement. [DevExpress ProgressPanel appearance and sizing properties](https://docs.devexpress.com/WindowsForms/DevExpress.XtraWaitForm.ProgressPanel._properties) were checked against the installed 25.2 implementation; no vendor source was copied.

A complete formula/constant/name/order/protection digest comparison is included. Observed populated recovery writes with metadata verification are approximately 13.4 seconds on this machine; this is not a controlled architecture benchmark.

Both Debug and Release build successfully. Final synthetic native recovery and progress fixtures pass in both configurations. Progress geometry and rendered PNGs were checked at normal, 150% and 200% text sizes, including unbroken long filenames, overflow scrolling, shrink-back, manager lifecycle and operation-guard cleanup. These font-size fixtures are not physical multi-monitor/DPI acceptance. Scheduler checks cover unavailable/minimised owners, start/completion messages and the unchanged dirty/Undo contract.

Excel tests use an independently owned instance with macros, events, links and calculation disabled; they open recovery XLSM and normal recovered XLSB without repair and SaveCopyAs to separate files. The 335 VBA module identities/source hashes, original custom XML/custom properties and a single unchanged recovery-history part survive all four outputs. Aggregate VBA source hash: `1539cc5c003414274742dda616da675ebf68b420e4143bd1ca5a7e17d68fa470`.

Round-trip differences are explicitly **not** hidden behind a blanket equality claim:

- Direct native recovery XLSM reread exactly preserves the live model's formula text, constants, global/local names, sheet order and protection digest.
- Excel SaveCopyAs of that recovery XLSM preserves every worksheet formula/constant/local-name/order/protection digest and all business names. Excel removes exactly six unused `=#NAME?` function-name placeholders: `_xlfn.ANCHORARRAY`, `IFERROR`, `IFNA`, `PERCENTILE.EXC`, `SINGLE`, and `SUMIFS` (each with `_xlfn.` prefix). The verifier classifies only these exact name/value pairs.
- Excel SaveCopyAs of the recovered **normal XLSB** adds implicit-intersection `SINGLE(...)` wrappers to **1,140 Development Expenditure formulas**. Constants, sheet order, protection and names match, but formula text is not identical. Independent full Summit recalculation before/after this Excel save agrees across **44,906 SOCI, SOFP, cashflow, Check Sheet and Development Expenditure cells** (numeric tolerance 1e-7). This is native-value evidence, not proof of Excel/VBA financial equivalence. [Microsoft explains implicit intersection](https://support.microsoft.com/en-us/excel/implicit-intersection-operator) and [Formula versus Formula2 translation](https://learn.microsoft.com/en-us/office/vba/excel/concepts/cells-and-ranges/range-formula-vs-formula2).

## Manual acceptance

1. Enable a short interval on a **disposable** plan; edit through DIT and wait idle. Confirm progress, `_recovery.xlsm`, normal Save still enabled, and Undo still works. Disable backup and verify settings persist across restart.
2. Simulate abandonment by closing without saving the original. Reopen the original: test Yes, No and Cancel; only a newer owned recovery should be offered.
3. Accept recovery and view history. Confirm last committed values/description, read-only previous-session entries, new-edit Undo, and refreshed output figures.
4. Save recovered plan as a new XLSB, then repeat with explicit original replacement confirmation. Confirm filename/summary/dirty state and that cancelling Save As leaves recovery mode active.
5. Open/save/recalculate in Excel **with the client's approved VBA policy**, then reopen in Summit. Financial, custom VBA, shared/network folder/permissions, multi-model, large-file x86/x64, and physical DPI acceptance remain manual.
